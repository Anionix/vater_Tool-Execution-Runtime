# Python先行型・安全なツール実行基盤 — 設計版 2.0.0

**目的：Pythonの純粋な計算を権限と入力境界の内側で安全に実行し、公式MCPのローカル標準入出力から呼び出せるようにする。**


## 結論

**Pythonで仕様・計算・認可・通信接続を先に試作し、公式MCPとの実接続を実測する。Rust、Lean、Kaniへの移行・形式証明は、必要性と費用対効果が確認できた機能だけに後から適用する。**

初期版は単一ローカル利用者、整数の安全な加算、ローカルMCP標準入出力のみ。外部変更、HTTP、APIキー送信、未信頼コード実行、GPUは初期公開に含めない。

## 保護する資産（`task.trust.001`）

| 資産 | 保護の前提 |
| --- | --- |
| 実行ファイル・設定・依存ファイル | ホスト管理者が書き込み権限を管理する。起動処理は固定されたコマンドと `config/limits.json` を使う |
| 認証情報 | 初期版の起動処理は子プロセスの環境を作り直す。親環境にある認証情報を渡さない |
| 操作履歴 | 記録付き拡張のデータベースはホストが指定する。履歴を置くファイルの読み書きはホストが管理する |
| 機密入力 | 標準入力から受け取るデータには機密が含まれうる。初期版の加算には整数だけを渡す |

## 入力の境界（`task.trust.002`）

| 入口 | 入力と検査を担当する部分 |
| --- | --- |
| 初期版の起動処理 | ホスト所有の設定から通信上限を読み、標準入出力の検査を起動する。起動引数は拒否する |
| 以前の起動名 `scripts/launch_guarded_mcp.py` | 空の環境で初期版の `scripts/run_local_mcp.py` へ引き渡す。起動引数も同じ入口で検査する |
| 開発用の中継処理 `scripts/guarded_stdio.py` | 子プロセスと上限を指定できるのはホスト。子の標準出力も、完全な一行・サイズ・深さ・形式を検査してから転送する |
| 公式サーバーの標準入力 | 通信の検査を通った要求を公式開発キットが解釈する。Python中核がツール名と引数を検査し、ホスト側の許可一覧で実行を判断する |
| 開発用の公式サーバー直接起動 | 標準入力を公式開発キットが受け取る。ホスト側の環境設定で記録付きツールを有効にできる |
| 開発用のローカル実行と記録付き実行 | 各コマンドが標準入力の一行ごとに読み取りと形式検査を行う。記録付き実行ではデータベースの場所をホスト側の起動引数から受け取る |
| 公式開発キットの制御メッセージ | 接続の初期化・一覧取得・呼出し・取消しは開発キットが振り分ける。要求識別子は通信上の対応付けに使う |
| ホストから読むファイルと環境 | 起動時に `config/limits.json` と加算の入力スキーマを読む。直接起動する開発用サーバーは `VERIFIED_EXECUTION_LEDGER_PATH` も読む |
| 記録付き拡張・復旧 | 操作台帳と取消し記録はホスト所有。クライアントが選べるのは要求キーと引数。履歴や復旧対象のファイルはホストが選ぶ |
| Pythonからの直接呼び出し | 呼び出し側がホストとして許可一覧を渡す。記録付き経路では利用者名とデータベースもホスト側で設定する |

初期版の唯一の公開ツール `checked_add` は、符号なし32ビット整数二つを検査して足す。SQLiteは記録付き経路の操作履歴を保管する。ファイルのアクセス制御はオペレーティングシステムが担う。

## 外部入力と権限

| 対象 | 初期版の規則 |
| --- | --- |
| 通信（`task.trust.004`） | ホストが起動した単一利用者の標準入出力を使う。HTTPで使う認可フローはHTTP対応の段階で扱う |
| ツールの説明とモデルの文章（`task.trust.005`、`task.trust.006`） | 説明文は表示用。モデルの文章は要求データとして扱う。受け取る加算引数は整数の `left` と `right` のみ。実行の可否はホストの許可一覧で決まる |
| 外部サービスの応答（`task.trust.007`） | 応答も未信頼の入力。別プロセスの加算結果を使うクライアントは、成功表示・構造化フィールド・厳密な整数型・範囲・元の二項との一致を検査して整数だけを取り出す。自由記述の返信は権限にも計算結果にも使わない。将来のサービスごとに、その処理に対応する意味の検査が必要 |
| ファイル・外部送信（`task.trust.008`、`task.trust.012`） | 初期版の公開ツールは加算だけ。ファイル書込み、任意のネットワーク通信、外部モデル呼び出しを登録せず、送信先の許可一覧は空とする。通信上の拒否とホストのファイルアクセス権は別々に検査する |
| 認証情報・利用者名（`task.trust.009`、`task.trust.010`） | 初期版の二つの起動名は同じ起動処理に合流する。親環境の認証情報と記録付き拡張の設定を子サーバーに渡さない。利用者名はホストが設定し、要求本文の自己申告は拒否する |
| 保存した結果（`task.trust.011`） | 初期版の純粋な加算は結果を保存しない。記録付き拡張では同じ利用者・同じ操作を照合し、要求受付時とデータベース読取り後にホストの権限を再確認する。プロセス内の単調時計が指定期限に達するか、ホストが失効を通知すると、値と操作識別子を返さない。ホストは失効通知を設定したままにし、再付与には新しい権限を使う |
| 規則がない操作（`task.trust.014`） | 未登録の操作を拒否する。登録済みの加算もホストの許可が空なら拒否する |

通信のサイズ・形式検査は起動時の中継処理が担当する。公式サーバーも、計算処理から受け取った成功値を返信前に元の加算引数と照合する。正しい形式に収まる誤答もあり得るため、受信側の加算用検査は元の二項に結び付けて結果を確認する。権限の失効はアプリケーションが結果を引き渡す時点まで照合する。既に相手に届いた値の回収や、別プロセスへの失効通知は保証の範囲外。

実装と仕様は [加算結果の受信処理](../src/verified_execution/client_result.py)、[ローカル権限](../src/verified_execution/core.py)、[公式のツール仕様](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)、[公式の通信認可仕様](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)。

## 操作の危険度と承認

`task.trust.013` の機械可読な分類は [ツール別の危険度](../contracts/tool_risks.json) に記録する。分類は読取り、状態変更、不可逆操作、コード実行の4種類。加算は読取りとし、SQLiteに履歴を書く記録付き加算は状態変更とする。ツール一覧との照合試験は初期版と記録付き拡張の両方を対象にする。

| 操作・状況 | ホストが行う判断 |
| --- | --- |
| 削除・外部送信・購入（`task.trust.015`） | 初期版では公開しない。将来公開する場合は明示的な承認を必須とする。台帳の予約は承認必須が既定で、信頼済みの加算処理だけが現行の実行経路で免除を明示する |
| 承認後に対象の版が変化（`task.trust.016`） | 版1への承認で版2の予約を開始しようとしたら拒否する。台帳は主体・ツール・対象・版・引数を照合する。外部側で対象が変わる実運用では、外部の更新時にも対象版を照合する必要がある |
| 処理結果が不明（`task.trust.017`） | 同じ要求を受け取っても再実行せず、結果不明を返す。確認できた結果だけを記録し、別の実行を開始する判断と区別する |

`task.trust.018` の依存パッケージはPython Package Indexを供給元とし、版と配布物のSHA-256を固定する。初期版はクライアントが指定する拡張を読み込まない。検証環境に実際に導入した配布物の取得元と検査値を [配布物の記録](../evidence/verified_tasks/task.trust.018.json) に保存する。[固定済みの一覧](../requirements-py313.lock)・[検査値を使う導入方法](https://pip.pypa.io/en/stable/topics/secure-installs/)

## 最小公開への9ゲート

1. `scope` — 目的と非目標。
2. `trust` — 信頼境界と禁止事項。
3. `contracts` — 入力、出力、識別子、エラー。
4. `runtime` — Pythonの中核、構築、上限。
5. `mcp_transport` — **公式Python開発キットで実際に通信**。
6. `authorization` — 拒否既定のホスト側権限。
7. `read_only` — 算術・認可・通信の実際の縦断接続。
8. `minimum_validation` — 独立試験、異常入力、新旧互換性。
9. `minimum_release` — 実証結果から公開可否を判定。

ゲートは前段階が終わらなくても個別の試験を行えるが、正式な完了は前提依存をすべて満たしたときだけ。

## 後続の任意段階

- `formal_verification`：必要ならRustへ部分移植し、LeanとKaniを使用。最初の9ゲートに**含めない**。
- `provider_adapters`, `http_interface`, `durable_operations`, `testing`, `operations`：目的と安全性検査を明確にした拡張。既存のPython SQLite実装を再利用できるが、本物の外部副作用は未検証。
- ブラウザ、WebAssembly、WebGPU、その他の通信形式は用途と計測結果が得られた場合のみ。

## 初期の安全境界と未検証事項

- 0.11.0のPythonソースは既存の実装参考。今後の設計変更だけで公式MCP適合を保証しない。
- 公式開発キットの実接続・配布環境でのセキュリティ検査が必須。
- 実行中止は外部副作用のロールバックではない。
- Python実行環境のメモリ隔離や不正コードのサンドボックス化は初期の保証外。
- 段階ゲートを通すには、対象ソース・試験・実行結果を結び付けた証拠が必要。

## ローカル契約の読み方

| 用途 | どこで値を決めるか | 検査できること |
| --- | --- | --- |
| 通信要求 | クライアントが指定する JSON-RPC の `id` | 公式開発キットが同じ値で応答する。通信単位の値を業務操作のキーには使わない |
| 業務操作・承認 | ホストが主体を決め、台帳が操作識別子を発行する | 同じ主体と要求キーの再送を識別する。ホストが `read_resource` を渡すと、台帳は実行を記録する直前に対象の所有者と現在版を読み、予約した主体と版に照合する。外部の更新側で行う条件付き書込みは別途必要 |
| 追跡・実行試行 | サーバーの生成時と各ツール呼出し時に識別子を発行する | 標準エラーの記録から、一つのサーバーで行った複数の呼出しをたどれる。記録付き加算を再送すると業務操作の識別子を再利用し、試行識別子を新しく発行する |
| 入力元・結果の出所 | 要求はクライアント、加算結果は検査済みのローカル計算、権限と許可先はホスト | 要求元は診断記録の `source`、結果の出所は応答の `_meta` に記録する。受信側は説明用メタデータを信頼せず結果を検証する |
| 公開元・提供元の追加情報 | ホストが選んだ実行元とツール名の組で許可を照合する | 公式開発キットの `_meta` は名前空間ごとに独立し、入れ子の追加情報も保持する。現在のモデル・入口別の対応機能とエラー分類は [対応表](../contracts/local_capabilities.json) にある |
| 保管する値 | 診断記録はホスト発行の識別子、固定の分類、経過時間に限定する | 生の引数、会話、通信要求の識別子、鍵、トークンを診断に転記しない。任意の記録付き入口の要求キーはデータベースに保存するため、呼び出し側は秘密を含まない専用の値を発行する |

`tools/list` は一覧、`tools/call` はツール呼出しに対応する。推論要求、資源の読取り、作業の制御にはそれぞれ公式開発キットの別の要求型がある。未提供の操作はエラーを返す。初期版の送信先は空で、モデル呼出しは行わない。[JSON-RPC の要求と応答](https://www.jsonrpc.org/specification)

入力・出力のバイト数と入れ子の上限は [運用設定](../config/limits.json) の値で受信側・送信側の両方で解析前に検査する。解析後は公開スキーマと厳密な整数検査を適用する。開発用の二つの行入力コマンドは4096バイト・32段、ホストの設定は4096バイト・1段、取消し記録の読込みは2048バイト・1段まで。台帳の構造化引数の検査値は最大32段、正規化後16384バイトまで。

## 契約を変更する手順

1. `task.contracts.022` の正本は `contracts/checked_add.input.schema.json` と `contracts/checked_add.output.contract.json`。公式サーバーは起動時に入力・出力スキーマを組み立てる。変更は正本で行い、公開されたスキーマを通信試験で照合する。
2. `task.contracts.010` と `task.contracts.023` の旧版サンプルは `contracts/expected_cases.jsonl` に保持する。1系のサンプルとその検査値を残して互換性を試験し、互換性を壊す場合は新しいメジャー版と専用のサンプルを追加する。[Semantic Versioning](https://semver.org/spec/v2.0.0.html)
3. `task.contracts.024` の操作型追加では、入口と対応機能、ホストが許す操作、危険度、成功と拒否の期待値を同じ変更に含める。実際の公開一覧と危険度の照合、および新しい操作の呼出し試験を通す。[危険度の正本](../contracts/tool_risks.json)

ローカル初期版の起動時は、ホストが承認した公開元・名前・版と、加算の実装・通信入口・入出力契約の検査値を照合してから中核を読み込む。実装を更新したときは対応する差分を確認して承認記録を更新する。ホストの設定・起動処理・残りのインストール先を保護する責任はホストにある。[承認記録](../config/local_tool.json)

任意の記録付き経路では、ホストが設定した対象の読み取り関数が所有者と版を返す。所有者の不一致・読取り時の版変更・許可の失効があると処理を開始しない。使用前の承認は台帳で取り消せる。許可先を照合する際にはツール名・公開元・送信先がすべて一致する必要がある。

`task.authorization.002` はホストが選ぶ利用者識別子を台帳に保存し、実行元サービスの識別子を公開ツールの提供元として返す。両者が同じ値になる設定は起動時に拒否する。

`task.authorization.018` の費用単位は登録済みツールの呼出し1回。埋め込みホストは `build_server(call_budget=...)` でサーバーインスタンスの上限を設定できる。再送や失敗を含め、実行前に1単位を引く。残量がゼロなら計算や台帳への予約を始めない。省略時は従来の動作を維持する。上限はプロセス内にあり、再起動をまたぐ会計には使わない。

## 永続化の時計と監査記録

`task.durable_operations.020` の承認とワーカーの期限は、同一ホストの台帳時計 `OperationLedger._now()` で比較する。期限はミリ秒の時刻として保存し、実行開始時は SQLite の書き込みロック取得後に読み直す。呼出し元が送る時刻は現在時刻として扱わない。プロセス内の権限期限・経過時間には単調時計を使い、台帳の時刻と直接比較しない。永続化は単一ホスト内が対象で、時計の巻き戻しや異なるホスト間の時刻整合は保証の前提外。ホスト時刻の異常が判明したら、新規実行を止め、未確定の操作を照合する。

`task.durable_operations.022` の保存・削除方針を以下に定める。現在は運用設計であり、期限による自動削除は未実装。

| 記録 | 保存期間と削除条件 |
| --- | --- |
| 標準エラーの診断 | ランタイム内には保存しない。ホストで収集する場合は、識別子・固定の結果分類・経過時間だけを30日で削除する。 |
| 未完了・結果不明の操作 | 照合が済むまで保持する。時間経過だけで削除や再送を許可しない。 |
| 完了済み操作と承認 | 同じ要求を受け付ける台帳の稼働期間中は、重複排除に必要な識別子と結果を保持する。台帳を廃止する際は入口を停止し、旧要求が再実行されないことを確認してから、台帳とバックアップを廃棄する。 |

要求キーには秘密を含めない。監査に不要な生引数や会話、トークンを診断へコピーしない。記録の短縮や部分削除を導入する場合は、古い要求の再送を拒否できることを試験してから有効にする。
